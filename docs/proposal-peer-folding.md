# 外部ピアの集約とフローテーブルの容量：設計案（#96）

状態：設計案、未実装。対象はイシュー #96。英語の設計文書 `docs/design.md` には、実装したときに反映する。

## 1. 問題

束ねたフローのキーには相手のアドレスが入る（`struct shawk_flow_key` の `raddr`）。インターネットに面したホスト（ロードバランサ、Web サーバ、公開 DNS や QUIC のサーバ）では、クライアントのアドレスごとに別のフローになる。数が効いてくるのは次の 4 か所である。

| 場所 | いまの振る舞い | 外部クライアントが多いと |
|---|---|---|
| カーネル | `flows_0` と `flows_1` は事前に確保したハッシュマップで、大きさは `-max-flows`（既定 16384、TCP と UDP で共有）。iter/tcp は毎インターバル、開いている接続ごとにそのキーを作り直す。 | 満杯になると `flow_get()` が新しいキーを捨て、`flow_drops` を数えるだけになる。同じホストのまれなバッチジョブのフローも巻き込まれる。 |
| エージェント | `otlp.State` は系列を 15 分（idle TTL）保持し、生きている系列すべての累積値を 15 秒ごとに送る（1 リクエストあたり最大 1000 系列、3 MiB）。 | 15 分間に現れたクライアントの数だけ系列が残る。1 系列はおよそ 10 データポイントで、毎インターバル送り直される。 |
| コネクタ、PostgreSQL | `shawk.edges` の一意キーに `remote_addr` が入り、保持期間は既定で 3 年。 | クライアントのアドレスごとに 1 行ずつ増え続ける。書き込み、`dependencies` などアドレスで突き合わせるビュー、prune がそのぶん重くなる。 |
| Prometheus | 相手アドレスはラベルにせず、`max_peers`（既定 50）を超えた相手は `~other` にまとめる。 | 影響しない。 |

取りこぼしは `shawk.agent.flows.dropped`、`shawk_v1.agents` の `dropped_flows`、アラート `ShawkFlowsDropped` で分かる。しかし、どの期間の観測が欠けたかは残らない。`unobserved()` はエージェントが止まっていた期間しか返さないので、「この期間に使われていない」という判断が、取りこぼした期間の上で成り立ってしまう。

## 2. 方針の要点

外部クライアントのアドレスを一つずつ持っても、契約のうちサービス単位の部分はそれを使っていない。`shawk.service_dependencies`、`known_dependencies`、`graph_edges`、`dependency_changes` は、サービスの分からない相手を `peer_class()` で `~external` などの名前にまとめている。Prometheus の `service.peer.name` も同じ名前を使う。外部クライアントの個々のアドレスが見えるのはアドレス単位のビュー（`dependencies`）だけで、そこでも相手にエージェントはなく、突き合わせる相手側のエッジもない。

そこで、外部のピアをカーネルの中で 1 つのキーにまとめる（以下「集約」と呼ぶ）。集約したキーの相手アドレスは `0.0.0.0/0`（IPv4）と `::/0`（IPv6）というネットワークで表す。この形には次の利点がある。

- `peer_class()` はこのネットワークを今のままでも `~external` と名付ける。サービス単位のビュー、`known_dependencies`、Prometheus の名前は集約の前と変わらない。
- PostgreSQL の `inet` はネットワークをそのまま保持できる。`dependencies` の突き合わせ（`c.local_addr = s.remote_addr`）はネットマスクも比べるので、集約したエッジがほかのホストのエッジと誤って結び付くことはない。
- キーの数は、外部クライアントの数ではなく、ローカルのエンドポイント（アドレス、ポート、プロセス）の数で抑えられる。

内部のピア（エージェントがいるかもしれない相手、エージェントのない社内の相手）のアドレスは今までどおり正確に残す。

## 3. 設計

### 3.1 カーネル：外部ピアの集約

- **分類表:** 新しい `BPF_MAP_TYPE_LPM_TRIE` の `internal_peers` を作り、エージェントが中身を入れる。キーは IPv4 射影の IPv6 アドレスと接頭辞の長さで、IPv4 の `a.b.c.d/n` は `::ffff:a.b.c.d/(96+n)` として入れる。表にあるアドレスは内部、ないアドレスは外部とみなす。
- **集約する場所:** 集約はキーを作るときに 1 回だけ行う。TCP では、キーを作った後の毎インターバルの走査（iter/tcp）はソケットのストレージにあるキーをそのまま使うので、集約の判断は接続ごとに 1 回で済む。
  - TCP の受信側: `on_passive_open()` と `adopt_tcp()`（`DIR_IN`）。
  - UDP のサーバ側: `handle_udp_send()` と `shawk_skb_consume_udp()` で、向きが `DIR_IN` に決まった後。
  - 送信側（`DIR_OUT`）は設定したときだけ（3.2）。TCP では、`ESTABLISHED` になったときに `read_sock_addrs()` がアドレスを読み直すので、その後で集約する。
- **集約したキーの形:** `raddr` をすべて 0 にし（IPv4 なら `::ffff:0.0.0.0`）、キーに新しいフラグ `KEY_FOLDED` を立てる。フラグのために `__u8 flags` を足すと、キーは 64 バイトから 72 バイトになる。`direction` の上位ビットを使えば大きさは変わらないが、読みにくいので勧めない。
- **費用:** LPM の検索が、新しい TCP 接続ごとに 1 回、UDP サーバのデータグラムごとに 1 回増える。UDP の経路にはすでにソケットストレージの検索とハッシュマップの更新があるので、それに比べて小さい見込み。`-bpf-stats` で実測して確かめる。
- **カーネルの版:** LPM トライは 4.11 から使える。対象の 5.14 以降で問題ない。

### 3.2 エージェント

- **設定:**
  - `-internal-peers`（既定 `private`）: 正確に残す範囲。`private` は `peer_class()` の非グローバルな範囲（RFC 1918、CGNAT、ULA、ループバック、リンクローカル）を指す。社内で公開アドレスを使っている場合は `-internal-peers=private,203.0.113.0/24` のように加える。
  - `-fold-external`（既定 `in`）: `in` はサーバ側だけ集約、`all` は送信側も集約、`none` は集約しない。送信側の宛先アドレスは「どの外部 API を呼んでいるか」を示すので、既定では残す。クローラ、メールリレー、フォワードプロキシのように宛先が多いホストでは `all` にする。
  - ホスト自身のアドレス（`host.ip` に載せるもの）は、自動的に内部として表に加え、毎インターバル更新する。公開アドレスだけを持つ VM が、自分の公開アドレスで自分に接続する場合に備えるため。
- **OTLP:** 集約したエッジでは `network.peer.address` を `0.0.0.0` または `::` にし、新しい属性 `shawk.peer.folded=true` を付ける。アドレスを空にしないのは、前の版のコネクタが `network.peer.address` を読めないエッジを捨てるため（`input.go` の `edge()`）。
- **診断に使う情報:** エージェントは自分の `-internal-peers` をリソース属性（`shawk.peer.internal`）で送る（3.3 の診断に使う）。
- `shawk flows` は、集約したフローの相手を `0.0.0.0/0` や `::/0` と表示する。

### 3.3 コネクタと PostgreSQL

- **入力:** `edgeID` に「集約」の印を持たせる（相手を `netip.Prefix` で持つ）。PostgreSQL には `remote_addr` を `'0.0.0.0/0'` または `'::/0'` の `inet` として書く。`network.peer.address` しかない前の版のエージェントのエッジは、今までどおり扱う。
- **相手の名前:** 集約したエッジは、相手のサービスを探さずに `classify()` で名付ける。結果は `~external` で、`peer_class()` と一致する。`shawk.peer.agent` は false になる。
- **スキーマ:** `edges.remote_addr` の型は `inet` のままで、移行は要らない。`peer_class()` も変えない。`docs/design.md` §6.2 の `dependencies` に、「`client_addr` が `0.0.0.0/0` や `::/0` の行は、集約した外部クライアントである」と書く。
- **数え方（§7）:** 集約したサーバ側のエッジは `shawk_peer_agent="false"` になるので、今までどおりサーバ側で数える。
- **診断:** コネクタは、エージェントのいるホスト A のクライアント側のエッジが、エージェントのいるホスト B に向かっているのを見たときに、A のアドレスが B の `shawk.peer.internal` に入っているかを確かめる。入っていなければ、B は A からの接続を集約してしまい、両側が突き合わなくなる。また §7 の規約では、A のクライアント側と B の集約したサーバ側の両方で数えられてしまう。そこで警告をログに出し、メトリクス `shawk_connector_folded_agent_peers` で数える。公開アドレスどうしで通信するホスト群で、`-internal-peers` の設定漏れを見つけるためのもの。

### 3.4 取りこぼした区間の記録

- **記録:** `agent_sessions` を upsert するとき、`dropped_flows` が増えていたら、前の `last_heartbeat` から新しい `last_heartbeat` までを新しい表 `shawk.partial_observations(host_id, started_at, since, until, dropped)` に記録する。隣り合う区間はまとめる。SQL の中で前の値と比べるので、コネクタが再起動しても、複数のコネクタがあっても正しく動く。エージェントの変更は要らない。
- **契約:** 新しい関数 `shawk_v1.partly_observed(since, until)` を足す。返す列は host、start、end、dropped。`unobserved()` の戻り値の型は変えない（列を足すには DROP が要り、契約が変わるため）。
- **Grafana:** 3 つのダッシュボードで、`unobserved()` の注釈の隣に「partly observed: host」の注釈を出す。fleet ダッシュボードの一覧にも出す。
- **文書:** §10 と README の「使われていない」の判断に、「取りこぼした区間を除いて判断する」と書き足す。
- prune は保持期間で `partial_observations` も消す。

### 3.5 テーブルの大きさ（第 2 段階、測ってから）

集約した後、キーの数は「内部のピアの数 × ローカルのサービスの数」で決まる。大半のホストは既定の 16384 に収まる見込み。ただし次のホストではあふれうる。

- 内部のクライアントがとても多いサーバ（何万ものクライアントを持つ DB）
- Pod の多い Kubernetes ノード

その場合は次のように対処する。

- **自動で大きくする:** 次に使うマップを、切り替える前に倍の大きさで作り直し、`ARRAY_OF_MAPS` の要素を入れ替える。条件は、前のインターバルで取りこぼしがあったか、使用率が 75% を超えたこと。Linux 5.10 からは、ハッシュの内側のマップは外側の定義と `max_entries` が違ってもよい。VM テストで確かめる。上限は新しい `-max-flows-limit`（例：`-max-flows` の 16 倍）。使用率の低い状態がしばらく続いたら、`-max-flows` まで戻す。
- **メモリ:** 1 要素はおよそ 180 バイト（キー、値、ハッシュの付帯情報）。16384 要素で 1 マップ約 3 MB、26 万要素で約 46 MB、マップは 2 つある。上限はこれを見て決める。
- **読み出しを速くする:** マップを空にする処理を、1 キーずつの `Delete` から `BatchLookupAndDelete`（5.6 以降）に変える。

## 4. 採らなかった案

| 案 | 採らない理由 |
|---|---|
| サービスごとのしきい値を超えた相手を集約する | どの相手が集約されるかが、インターバルの中での到着順で決まる。同じクライアントが、ある時は正確なキー、ある時は集約したキーになり、PostgreSQL の突き合わせが不安定になる。サービスごとの数をカーネルで数える状態も要る。 |
| 外部ピアだけ LRU マップにする | LRU はインターバルの途中で黙って要素を追い出すので、追い出された分の数が失われる。取りこぼしなら少なくとも数えられる。集約すれば外部のキーは少ないので、LRU は不要になる。 |
| `/24` などの接頭辞にまとめる | インターネット全体では、それでも数に上限がない。サービス単位では結局 `~external` になるので、得るものもない。 |
| `-max-flows` を大きくするだけ | メモリが比例して増え、エージェント、OTLP、PostgreSQL の負荷は減らない。 |
| サンプリング | まれな依存を見逃さないという中心の約束に反する。 |
| 内部の範囲をコネクタから配る | OTLP には、コネクタからエージェントへ設定を返す経路がない。エージェントはデータベースにもつながない。代わりに 3.3 の診断で、設定のずれを見つける。 |

## 5. 互換性と移行

- **振る舞いの変化:** 既定で集約するので、外部クライアントのアドレスは記録されなくなる。不正アクセスの調査などでアドレスが要る場合は `-fold-external=none` にする。CHANGELOG に明記する。
- **上げる順:** コネクタを先に上げる。前の版のコネクタは、新しいエージェントの集約したエッジを `0.0.0.0` / `::` という 1 つのアドレスとして保存する。コネクタの `classify()` も `peer_class()` も、その相手を `~unresolved` と名付ける。名前がずれるだけで、データは失われない。
- **契約:** `shawk_v1.partly_observed()` を足すだけで、既存のビューと関数は変えない。`dependencies` の `client_addr` に、ネットワークが入りうることを文書に書く。
- **キーの構造:** キーが変わると BPF オブジェクトと bpf2go の型を作り直すことになる。#94 / #95 の作業（別ブランチ）とは `shawk.h` と `shawk.bpf.c` で衝突しうるので、あちらを先に取り込んでから進める。

## 6. テスト

- **BPF（`make test-root`、VM テスト）:**
  - ネットワーク名前空間と veth を作り、`198.18.0.0/15`（RFC 2544 のベンチマーク用で、`private` に入らない）と `10.0.0.0/8` のクライアントからサーバに接続する。前者は集約したキーに、後者は正確なキーになることを確かめる。
  - 同じことを UDP、起動前からある接続、`-fold-external=all` の送信側、`none` でも確かめる。
  - `-max-flows` を超える数の外部クライアントで、取りこぼしが出ないことを確かめる。
- **互換性:** `TestKernelCompatibility` / `make compat`（Rocky 9.6 の BTF）。
- **エージェント:** 集約したフローを OTLP の属性に変換するテスト（golden テスト）。
- **コネクタ:**
  - `shawk.peer.folded` を `inet` のネットワークにすること、相手の名前、前の版のエージェントの入力。
  - PostgreSQL のテスト: `dependencies`、`service_dependencies`、`known_dependencies` でネットワークの行が `~external` になること、`partial_observations` の記録とまとめ、`partly_observed()`。
- **e2e:** 公開アドレスの範囲を使う複数ホストの構成で、集約と 3.3 の診断を確かめる。
- **性能:** UDP を大量に送り、`-bpf-stats` で集約の前後のプログラムの実行時間を比べる。

## 7. 段階

1. **第 1 段階（このイシューの中心）:** 3.1〜3.4、文書、CHANGELOG。
2. **第 2 段階:** 3.5。第 1 段階の後、内部のピアだけで取りこぼしが出るかを測ってから決める。
3. **別イシュー:**
   - アドレス単位のエッジの保持期間を、サービス単位の `known_dependencies` より短くする。内部でも Pod のアドレスは入れ替わり続けるので、`shawk.edges` は外部クライアントを集約しても増え続ける。いまは prune がすべての表を同じ保持期間で消している。
   - 取りこぼしたときに、相手を持たない「あふれ」キーにフローを退避して、少なくとも「このポートが使われた」ことは残す案。

## 8. 決めてほしいこと

1. 集約を既定で有効にするか（`-fold-external=in`）。勧めるのは有効。
2. フラグの名前（`-internal-peers`、`-fold-external`）と、`private` という既定値の書き方。
3. 第 1 段階に 3.4（取りこぼした区間の記録）を含めるか。勧めるのは含める。
4. 7 の別イシュー 2 件を起こすか。
